# Seller pending-to-held foundation

This internal PostgreSQL-only increment consumes the authoritative paid-sale and fulfillment lifecycles. An order is eligible only when it is `COMPLETED`, `PAID`, `CONFIRMED`, and has no `OPEN` or `UNDER_REVIEW` dispute. Its single payment must be `PAID`, have `paidAt`, use BRL, and equal the order total. Exactly one structurally valid `SALE_RECOGNIZED` posting for `OrderSale/<order id>`, including `sha256("sale-recognition:v1:" + order.id)`, is mandatory.

The immutable order snapshot is the sole value authority: `sellerProceedsMinor = totalAmountMinor - platformFeeAmountMinor`. No current fee policy is consulted and negative proceeds fail closed. Positive proceeds are posted only through `FinancialLedgerService.postWithOutcome()` as DR `SELLER_PENDING` / CR `SELLER_HELD`, with `type = SELLER_FUNDS_HELD`, `referenceType = OrderSellerHold`, and `sha256("seller-pending-hold:v1:" + order.id)`. PostgreSQL additionally permits at most one such posting per order.

The ledger remains the monetary source of truth. Authoritative Order/Payment/recognition validation, each positive posting, and its `FinancialHold` are committed in one SERIALIZABLE transaction. The hold is correlated to the order, payment, seller, and exact posting through `ledgerTransactionId`, with reason `DELIVERY_PROTECTION`, status `ACTIVE`, BRL snapshot proceeds, and `releaseEligibleAt = null`. `Settlement` is deliberately not used: the local hold already represents this protection phase, while settlement would duplicate lifecycle state. A valid zero-proceeds order creates no ledger transaction, entry, hold, or settlement; the non-monetary `SellerPendingHoldZero` row durably records completion and prevents a batch busy loop without representing a balance.

Order locking precedes ledger account locking. Delivery-protection holds have database-enforced required fields and lifecycle invariants. Zero-marker replay is validated against the authoritative order, payment, seller, and zero proceeds. Partial artifacts either fail closed into reconciliation or repair only a missing hold for an already-valid posting. Deterministic ledger idempotency, unique database constraints, and advisory locks serialize workers. Existing postings and holds are revalidated rather than trusted. Failures create a deduplicated open `ReconciliationIssue` for `SellerPendingHold/<order id>` and return an outcome so the issue commits. Open/investigating issues block batch retry; resolved issues permit reevaluation. Active disputes are expected business blocks and do not create reconciliation.

No PSP, HTTP, webhook, cron, timer, refund, withdrawal, or order/fulfillment mutation occurs. No entry touches `SELLER_AVAILABLE` or `SELLER_RESERVED`. **Held funds are not yet release-eligible because release policy is a future increment.** The next financial increment, not this one, owns `SELLER_HELD → SELLER_AVAILABLE`.
